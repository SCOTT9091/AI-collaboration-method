为什么不叫“提示词工程”？因为写提示词只是协作五个步骤中的一步（交底）。决定产出质量的，还有动笔前想清楚要什么、拿到结果后加以验证，以及跨会话的沉淀。“上下文工程”更接近一些，但仍偏重“给模型输入什么”，没有涵盖目标定义和验收。因此本文称之为“AI 协作”：把 AI 当作受托的执行者，讨论如何在信息不对称的条件下做好委托。

## 一、基本认识

把模型想成一位能力很强的新同事：知识面广，但不了解你的处境，也不能随时追问。它交出的东西，责任仍在你。

大语言模型的基础架构是 Transformer，它最初就是为机器翻译提出的。借翻译的视角来看协作，可以得到三个检验点：原文是否清楚，译者是否了解背景，译文是否准确。对应到协作中：你的意图是否表达清楚，AI 是否掌握了必要的背景，产出是否符合你的意图。这三点分别对应后文的明确、交底和验收。

从这个角度看，下面五种场景是同一件事，只是方向不同：

- 你 → AI：让 AI 理解你的意图
- 现场 → AI：把设备型号、硬件配置、运行现象等现实信息，转写成 AI 能分析的形式
- 材料 → 你：让 AI 帮你读懂陌生内容
- 专业 ↔ 专业：在业务、工程和不同专业之间转译术语与前提
- 想法 → 结论：让 AI 把零散、模糊的想法整理成有结构的分析

其中“现场 → AI”和“专业 ↔ 专业”在工程项目中最常见，第六节单独展开。

## 二、五个步骤

| 步骤 | 做什么 | 要点 |
| --- | --- | --- |
| 明确 | 想清楚要什么、什么算对 | 先写验收标准，再写任务；说明期望的完整程度；让 AI 复述你的理解，并向你提问；反例可以给，但要同时说明期望的做法 |
| 交底 | 只交给 AI 必要的信息 | 任务、背景、约束、输出形式；要求附上原因；有原件就给原件，有示例就附上 |
| 推进 | 分步执行 | 规格写成文件后，开新会话执行；大任务拆小，每步的产出可检查，并作为下一步的输入 |
| 验收 | 检查产出 | 回译（让 AI 还原成需求，由你比对）；让 AI 逐条给出依据，而不是问它“有没有问题”；开新会话或换角色审核 |
| 沉淀 | 审核后入库 | 成为下一轮高信噪比的上下文，回到“交底” |

### 明确：三种模糊

- 不知道要什么：让 AI 列出几种选项，由你来挑
- 知道但说不清：让它复述、追问；读它的复述，是成本最低的检验
- 说得清但漏了：用清单核对背景和约束

两点补充：模型倾向于按最小范围理解需求，想要完整的版本就要明说，比如“边界情况和异常状态都要处理”。想清楚之后，把规格写成文件，再开新会话执行，让执行从干净的上下文和明确的完成标准开始。

### 交底：写清意图，而不是堆砌规则

- 附上原因：知道为什么，模型能举一反三。只写“选宽温型元器件”，它只会照做这一条；写明“设备装在户外，冬季最低 −30 ℃”，它还会顺带考虑电池、显示屏、线缆和密封
- 写原则，不穷举规则：把所有边界情况塞进提示词，只会让它更僵硬；用几个典型示例代替
- 正面说要什么：反例可以给，但要同时说明期望的做法
- 有原件就给原件：文件、截图、日志直接附上，不要转述（前提是可以外发，见第七节）
- 同事测试：把提示词给一位不了解情况的同事看，他看不懂，AI 多半也看不懂
- 不容例外的规则，不能只靠提示词：提示词里的要求，模型多数时候会照做，但无法保证。涉及安全、权限、不可逆操作的规则，要靠程序、权限设置或审批流程强制执行
- 反复强调没有用：加“重要”“必须”，往往只会让它过度执行。总被忽略时，要么精简上下文，要么改用强制手段

### 验收：按难度分层

- 能机械检查的（格式、测试、引用），交给程序，最好是 AI 自己能运行的检查
- 要对照来源的，抽样核对
- 涉及品味和决策的，只能由人判断，不要指望自动化

几点说明：

- 验证通常比生成省力，所以能让 AI 生成、自己来验的，就别自己生成。但高度专业的内容，验证同样要有专业能力。
- 回译：让 AI 把它写的规格或总结还原成一句话需求，再由你对照原始需求。比对必须自己做：AI 复述的是它自己的理解，如果它理解错了，复述里也会带着同样的错误。
- AI 自查容易偏袒自己的产出。可以开一个新会话、换个角色，或要求它逐条给出依据。
- 给 AI 一个能自己运行的检查（测试、脚本、对照样本），它就能自己发现错误、自己修正。要求它附上实际运行的命令和输出，而不只是一句“已通过”。
- 让 AI 审核时，给它对照的规格，并说明哪些不用管。只让它“找问题”，它总能找到一些；照单全改，反而会过度设计。

### 放手执行前：五个问题

让 AI 无人值守地长时间执行之前，先回答五个问题：

1. 完成标准是什么？比如规格文件、必须通过的测试
2. 它能自己检查吗？比如测试、脚本、审核步骤
3. 允许它动哪些东西？权限和范围要事先划定
4. 什么时候必须停？设定轮数、时间或花费上限
5. 结果交给谁签收？不可逆的操作由人批准

## 三、为什么这样做

上面的做法，大多可以从大语言模型的几个基本机制推出：

| 机制 | 做法 |
| --- | --- |
| 注意力：无关信息会分散重点 | 精简上下文。取舍只看一条：这条信息会不会改变输出？会就留，不会就删。实际中，信息不足比信息过多更常见 |
| 自回归：前面生成的内容会约束后面的输出 | 分步推进，审核后再往下走。推理模型自带思考，“一步步想”之类的措辞作用有限，思考深度主要由模型设置控制 |
| 上下文学习：能从示例中归纳模式 | 示例通常比规则有效。示例之间要有差异，并说明哪些是要学的、哪些只是偶然特征，否则会被照搬 |
| 训练分布：输出倾向于训练语料中常见的写法 | 角色设定会调动语料中对应的视角和语气，但对准确率的作用因任务而异。先写清任务和背景，比设角色重要 |

另外三点：

- 模型倾向于迎合你，你的暗示会被放大，提问时要保持中立
- 输出有随机性，重要任务可以多生成几次对比，或收紧约束（固定格式、给出示例）
- 部分模型对长上下文中间部分的关注较弱，重要内容放在开头或结尾

以上机制并不完整，只列了与日常使用最相关的几条。思维链、检索增强、工具调用、多轮审核等常见技巧，都是这些机制的组合运用。

## 四、结果不好时先查哪里

1. 自己没想清楚要什么（最常见）
2. 想清楚了，但没写出来（隐性知识没说）
3. 信息不足、过多，或相互矛盾
4. 任务超出模型能力（精确计算、最新事实、长链推理），需要换工具或加验证
5. 随机波动，需要多生成几次，或收紧约束

调整提示词时，用 3 到 5 个固定用例（含一个边界用例）测试，一次只改一处，否则分不清哪次改动有效。

同一个问题纠正两次仍不对，不要再追加第三次。失败的尝试留在上下文里，会继续干扰它。开一个新会话，把学到的写进新的提示词。

## 五、知识库：外置的记忆与筛选

模型内部如何分配注意力，你无法干预；但每一轮给它看什么，由你决定。知识库就是由你把关的这道筛选，同时充当模型的外部记忆，弥补它无法跨会话记忆的缺陷。因此，知识库存放的不是聊天记录，而是经过审核、对后续决策有用的结论。形式上，建议用 Markdown 文件维护，人和 AI 都能直接读写。

### 入库条件（两条都要满足）

1. 已审核：有来源或依据，或经人确认。推测不能当事实存。
2. 会影响后续决策：不知道这一条，下次就会做出不同的选择，才值得存。

未经验证但可能有用的，可以例外入库，但必须标为“待验证”。过程中的草稿和试错不存，只留结论和理由。

### 六类条目

| 类别 | 内容 |
| --- | --- |
| 事实 | 已确认的信息，附来源 |
| 决策 | 选了什么、为什么选、放弃了什么。只存结论不存理由，以后就无法判断它是否还成立 |
| 约定 | 术语、命名、格式、边界 |
| 待解决 | 悬而未决的问题：谁负责，卡在哪 |
| 范例 | 好的示例、参照样本 |
| 原始材料 | 原文、长文档、数据。不常驻，只建索引 |

### 三层结构：按加载频率

- 常驻层（如 CLAUDE.md、AGENTS.md）：每次都载入，控制在一两页。放项目简介、当前目标、关键约定、硬约束和索引。判断标准：每个任务都用得上吗？它自己能查到吗？不是每次都用、或它能自己查到的，就不放；反过来，同一件事纠正过两次，就该写进去。
- 按需层：事实、决策、约定等，任务相关时才取。
- 归档层：原始材料和已被取代的旧条目，不主动加载。

每条都要有三项：状态（待验证 / 已确认 / 已取代）、出处、日期。

### 维护

- 新条目取代旧条目时，不直接覆盖：旧条目标为“已取代”，注明被哪条取代，再移入归档，这样日后能查到当初为什么改。
- 两条结论冲突时，由人裁决并记录，不让 AI 自行取舍，也不要两条并存。
- 合并摘要时先求全，再求精：先确保关键信息不漏，再删去冗余。保留出处，并用回译核对，防止多次摘要后失真。
- 每个阶段结束时清理一次：不再影响决策的归档；待解决项要么推进，要么明确放弃。

### 最小工作循环

1. 开始：载入常驻层和本任务相关的条目
2. 推进：分步执行，每步的产出可检查
3. 验收：AI 逐条给出依据，回译，人工审核；风险高、被大量引用的结论重点审核
4. 沉淀：只写入通过审核的结论和决策，附理由、状态、出处
5. 收尾：让 AI 列出本次新增、变更、被取代的条目，你确认后更新索引

### 常见问题

| 问题 | 对策 |
| --- | --- |
| 以讹传讹：错误结论入库，后续都建在它上面 | 守住入库条件，关键事实附依据 |
| 虚实不分：推测被当成事实 | 每条标状态 |
| 越积越杂：条目越存越多，抓不到重点 | 只存会影响决策的，分层 |
| 层层失真：多次摘要合并后意思变了 | 保留出处，合并时回译 |
| 不知所以然：条目缺理由和适用范围，别人看不懂 | 每条写明理由和范围 |
| 贪多求全：觉得“全给它更保险”，全量加载 | 按任务取，信噪比优先 |

## 六、工程中的两个场景

### 现场问题：把现实转写成文字

AI 看不到现场，它对现实的全部了解，都来自你转写的信息。转写的质量，决定了它推理的上限。

- 标识要精确：写型号、固件版本、配置参数，而不是“那台老设备”“新版本”
- 参数以规格书为准：附上手册相关页，不要依赖模型的记忆，它可能记错具体型号的参数
- 观测与推断分开：哪些是测到、看到的，哪些是你的猜测，分别标明
- 给原始数据：报错原文、日志片段、测量值（带单位和测量条件），不要只给你的概括
- 交代环境和边界：工况、负载、温度、接线或拓扑，以及哪些条件不能改动
- 写明已做过的尝试：做过什么、结果如何，避免它重复推荐

现场问题适合按“假设—检查—回传”循环推进：

1. AI 根据现象列出可能的原因，按可能性和排查成本排序
2. 对每个原因，给出能在现场执行的检查方法和预期结果
3. 你执行检查，把结果原样回传
4. AI 排除或收窄范围，进入下一轮

在这个循环里，你是 AI 的眼睛和手：它负责推理，你负责观测和操作。涉及安全或不可逆的操作，必须由人确认后再执行。

### 跨专业协作：在专业之间转译

大型系统项目的成员来自机械、电气、软件、工艺等不同领域。同一个词在不同专业里含义不同，各方默认的前提也不同，很多分歧其实只是表达不一致。AI 的知识覆盖面广，适合充当专业之间的译者，也适合整理各方的推理和观点。

- 转译：把一个专业的表述改写成另一个专业能理解的语言，并指出其中隐含的前提和单位
- 对齐术语：整理术语对照表，标出同词异义、异词同义，存入知识库的“约定”
- 整理观点：把各方意见拆成主张、依据和前提，标明出处，列出共识与分歧
- 区分分歧：哪些来自术语或前提不同，哪些是真正的方案之争

需要注意：

- 转译结果要请原作者确认（即回译），AI 在专业细节上同样可能出错
- AI 倾向于把分歧调和成一致。真正的分歧要保留原样，由负责人裁决并记录
- 每条观点保留出处：谁提出、何时提出、依据是什么

## 七、数据安全与学术规范

使用外部 AI 服务，等于把信息交给第三方。前文建议“有原件就给原件”，前提是这些信息允许外发。

### 数据安全

- 上传前先分级：公开资料可以直接用；内部资料脱敏后再用；涉密信息和受保密协议约束的内容，不得上传到外部 AI 服务
- 涉密项目按单位保密规定执行。确需 AI 辅助的，使用经单位批准的本地部署模型或内网环境
- 脱敏：去掉单位名称、人名、地理位置、合同金额和未公开的关键参数，用代号替换；代号对照表单独保存，不上传
- 了解服务条款：确认对话是否会被用于训练、保存多久、存放在哪里；能关闭训练授权的，就关闭
- 最小权限：让 AI 操作文件或系统时，只给完成任务所需的权限；项目资料不要放在公开分享的链接里
- 知识库同样要分级：含敏感信息的条目单独存放，不放进会提交给 AI 的常驻层

### 学术规范

- 如实声明：论文、报告、基金申请中使用了 AI 的，按学校、期刊和资助机构的要求，说明用在哪里、用到什么程度
- AI 不能署名：作者身份和学术责任由人承担
- 引用逐条核实：AI 给出的文献、标准号、数据可能是编造的，必须查到原文再用
- 数据必须真实：AI 可以协助分析和撰写，但不能生成或修饰实验数据
- 未发表的成果谨慎外发：尚未公开的研究思路和数据，上传后就脱离了你的控制，可能影响论文发表和专利申请
- 保留过程记录：关键结论要能追溯到对话记录或知识库条目，便于复核

## 八、迁移到其他场景

写提示词、写需求、带人、外包、做研发，面对的是同一个问题：信息不对称下的委托。成败取决于两点：能否把脑子里的东西转化为对方能执行的形式，能否设好检查点。

| AI 协作 | 研发中的对应 |
| --- | --- |
| 明确：目标与验收标准 | 需求评审、验收标准 |
| 交底：背景加示例 | 需求文档、技术交底、参考设计 |
| 推进：分步加检查点 | 分阶段交付、阶段评审 |
| 验收：回译、抽样、换视角 | 评审、测试 |
| 沉淀：分层知识库 | 文档管理、知识管理 |

## 一句话总结

先想清楚要什么，只给必要的信息，用示例说明，分步推进、逐步验收，审核过的结论再沉淀下来。
